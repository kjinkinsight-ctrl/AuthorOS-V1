# ADR-0005: Portable AuthorOS Archive

## Status

Accepted for M1 implementation

## Date

August 17, 2026

## Decision

AuthorOS will use `.authoros` as the extension for a versioned ZIP container containing normalized creative data, managed assets, migration provenance, and SHA-256 integrity metadata.

The archive is the canonical portability and restore format. It is not a renamed live SQLite database and does not expose application settings, account secrets, sync device identity, or profile email by default.

## Goals

- restore a project, series, or universe on another supported installation
- preserve stable IDs, scopes, links, unknown extension fields, and assets
- permit streaming export/import for large manuscripts and graphs
- validate all content before committing imported data
- survive internal database implementation changes
- provide enough provenance to diagnose legacy migrations
- support deterministic comparison of creative content
- make partial corruption and unresolved links visible rather than silent

## Non-goals

- incremental cloud synchronization
- live database backup through raw file copying
- executable plugin distribution
- application preferences or license transfer
- encrypted archive version 1
- collaboration history or remote audit logs

Encrypted archives may be introduced through a new archive-format version. Renaming an encrypted or proprietary blob to `.authoros` without a documented format is prohibited.

## Container layout

```text
manifest.json
data/
  scopes.jsonl
  record-types.jsonl
  records.jsonl
  links.jsonl
  manuscripts.jsonl
  manuscript-nodes.jsonl
  studio-views.jsonl
  writing-sessions.jsonl          optional
content/
  scenes/{sceneId}.json           scene document bodies
  notes/{recordId}.json           optional large rich-text bodies
assets/
  {assetId}/{sanitizedName}
checksums.json
reports/
  migration.json                  present when legacy migration occurred
  unresolved-references.json      present when unresolved references exist
```

JSON Lines files contain one UTF-8 JSON object per line. Empty optional collections may be omitted. Paths use `/` separators regardless of the creating platform.

## Why normalized export instead of a database copy

- SQLite schema versions are application implementation details.
- A normalized archive can be imported after table layouts change.
- Individual entries can be checksummed and diagnosed.
- Assets and large rich-text documents can be streamed.
- Stable ordering permits meaningful content fingerprints.
- Import can validate domain invariants before opening a write transaction.
- The archive can be inspected with standard ZIP and JSON tooling.

Raw database snapshots may be used internally for crash recovery, but they are not the user-facing portable format.

## Manifest

`manifest.json` must validate against [authoros-archive-manifest-v1.schema.json](../schemas/authoros-archive-manifest-v1.schema.json).

Required identity fields:

- `archiveFormat`: always `authoros`
- `archiveVersion`: integer format version, initially `1`
- `archiveId`: globally unique export ID
- `createdAt`: UTC ISO-8601 time
- `createdBy`: AuthorOS application version and platform
- `contentScope`: `project`, `series`, `universe`, or `library-selection`
- `rootIds`: stable IDs of the exported roots
- `schemaVersions`: domain component versions represented in the archive
- `entries`: metadata for every file other than `manifest.json` and `checksums.json`
- `contentFingerprint`: deterministic SHA-256 fingerprint of normalized creative entries

Optional fields include display title, description, source installation ID hash, migration summary, and extension data.

## Entry metadata

Every archived file other than the manifest and checksum file has one manifest entry:

```json
{
  "path": "data/records.jsonl",
  "role": "records",
  "mediaType": "application/x-ndjson",
  "bytes": 18420,
  "sha256": "lowercase-64-character-hex",
  "recordCount": 250
}
```

Entry paths must be unique after case folding on Windows. The checksum covers the exact uncompressed bytes stored for that logical entry.

## Checksums

`checksums.json` contains:

- checksum algorithm, fixed to `SHA-256` in version 1
- archive entry path to digest mapping
- the content fingerprint

The manifest repeats each entry checksum so import can validate metadata before trusting `checksums.json`. A mismatch between the two is a fatal validation error.

The ZIP container's CRC is not accepted as a substitute for SHA-256.

## Deterministic content fingerprint

Two exports with identical creative content should have the same `contentFingerprint` even if export time, archive ID, ZIP compression, or creating platform differs.

Fingerprint input is generated by:

1. normalizing all creative JSON to UTF-8 with `\n` line endings
2. sorting object keys lexicographically for fingerprint serialization
3. sorting JSONL entities by stable ID, then type
4. sorting archive entry paths by Unicode code point
5. hashing each normalized creative entry
6. hashing the ordered sequence `path + NUL + entryDigest + LF`

The fingerprint excludes `manifest.json`, `checksums.json`, volatile export timestamps, local file paths, device identity, and diagnostic timing data. It includes managed asset bytes.

## Data contracts

### Scopes

Each scope entry contains stable ID, scope type, parent scope ID where applicable, title, status, schema version, timestamps, revision, and extension data.

### Record types

Record-type entries contain built-in/custom identity, field definitions, allowed link types, template version, presentation defaults, and extension data.

### Records

Record entries follow ADR-0003 and include stable ID, type ID, owning scope, title, status, schema version, fields, tags, timestamps, revision, and extension data.

### Links

Link entries include stable link ID, source ID, target ID, type ID, direction, owning scope, optional validity bounds, label, metadata, timestamps, revision, and extension data.

### Manuscripts and nodes

Manuscript metadata and ordered nodes are exported separately from scene bodies. Node entries retain parent ID, order key, status, timestamps, revision, and content-entry path. Scene text is stored as a structured JSON document under `content/scenes/`.

### Assets

Asset records are exported with the records collection and point to managed paths under `assets/`. The archive path is derived from asset ID and a sanitized display filename, never from an original absolute path.

### Unknown fields

Unknown data from a newer schema must be retained in explicit `extensionData` maps. An older client may read known fields, but it cannot overwrite the archive in place or silently drop extension data during import/export.

## Migration report

When any source data was migrated from AuthorOS 1.x or another format, `reports/migration.json` contains:

- report version
- source format and detected versions
- target domain schema versions
- migration start and completion times
- transformations applied, each with ID and version
- source keys or files consumed
- source keys or files ignored and why
- generated IDs and their source identities
- repaired parent/order references
- warnings and errors
- unresolved-reference count
- pre-migration backup identity and fingerprint
- migration implementation/application version

The report must not include manuscript excerpts, profile email, secrets, or absolute user paths.

## Unresolved-reference report

Ambiguous or missing name-based relationships are preserved as unresolved references. The report includes:

- generated unresolved-reference ID
- source entity ID and source field
- original normalized label
- expected target types and scopes
- candidate target IDs, if ambiguous
- reason code
- suggested user action

Importing an archive with unresolved references is permitted when the manifest declares them. The application must surface them after import. Dangling canonical ID links not declared in this report are validation failures.

## Export algorithm

1. Resolve the selected root scope and all included descendants.
2. Freeze a consistent repository read transaction or snapshot.
3. Enumerate records, links, nodes, views, content, and managed assets.
4. Validate scope ownership and reference integrity.
5. Write normalized entries to a temporary archive.
6. Calculate entry sizes and SHA-256 digests while streaming.
7. Produce migration/unresolved reports when applicable.
8. Calculate the deterministic content fingerprint.
9. Write `checksums.json` and `manifest.json` last.
10. Reopen and validate the temporary archive.
11. Atomically replace the selected destination file.

Export failure leaves the prior destination and local project unchanged.

## Import algorithm

Import has a validation phase and a commit phase.

### Validation phase

1. Open the ZIP without extracting it to arbitrary paths.
2. Enforce compressed/uncompressed size and entry-count limits.
3. Reject absolute paths, drive prefixes, `..`, NUL, backslashes, duplicate paths, and case-fold collisions.
4. Parse and validate the manifest schema and supported archive version.
5. Require every declared entry and reject undeclared content entries.
6. Stream each entry and validate size and SHA-256.
7. Parse JSON/JSONL with line and entry limits.
8. Validate IDs, scopes, types, parentage, links, revisions, and asset references.
9. Verify content fingerprint.
10. Build an import plan and show warnings, unresolved references, collisions, and required choices.

### Commit phase

1. Create and verify a local pre-import backup.
2. Stage assets under generated temporary names.
3. Open one database transaction.
4. Insert or map scopes, types, records, links, manuscripts, nodes, and views.
5. Move staged assets into managed storage only after data writes validate.
6. Commit database changes.
7. Record import provenance and health state.
8. Remove temporary files.

Any failure rolls back database changes, removes staged assets, and leaves the prior library readable.

## Collision policy

When imported IDs already exist:

- identical entity fingerprints may be reused after user confirmation
- different content cannot silently overwrite an existing entity
- import may replace an explicitly selected existing root after a verified backup
- import may clone with a complete ID remap applied to every internal reference
- merging is deferred unless a domain-specific merge plan exists

Titles never determine identity.

## Security limits

Version 1 import enforces configurable limits with conservative defaults:

- maximum archive compressed size
- maximum total uncompressed bytes
- maximum individual entry bytes by role
- maximum entry count
- maximum compression ratio
- maximum JSON nesting depth
- maximum JSONL line length and record count
- maximum asset dimensions where decoding is required
- allowed media-type and extension combinations

Executable files, symbolic links, device files, and archive-within-archive expansion are rejected. Assets are treated as untrusted and are never executed.

Suggested initial desktop defaults must be validated against the large fixture before release:

- 4 GiB total uncompressed archive
- 2 GiB individual managed asset
- 100,000 entries
- 200:1 maximum compression ratio
- 16 MiB JSONL line

Android may apply lower device-aware limits and present a clear capacity error before extraction.

## Privacy

Included by default:

- selected creative scopes and content
- project-specific views and preferences required to reconstruct the work
- managed creative assets
- migration and unresolved-reference reports

Excluded by default:

- profile email and account identifiers
- license and authentication tokens
- sync device ID, queue, revisions, and cursor
- absolute local paths
- backup destination history
- analytics identifiers and crash reports
- community visibility and social profile settings

Optional author metadata must be separately selected and declared in the manifest.

## Compatibility policy

- Importers reject archive versions newer than they support without mutation.
- New optional entries may be introduced only when old importers can safely ignore them through declared roles and extension data.
- Breaking path, checksum, identity, or semantic changes require archive version 2.
- Domain schema versions can advance within archive version 1 when migration adapters preserve archive semantics.
- AuthorOS retains test fixtures for every released archive version.

## Validation gate

M1 archive implementation is complete when:

1. simple and large fixture round trips preserve IDs, content, links, and assets
2. two exports of unchanged content have the same content fingerprint
3. corrupted bytes, missing entries, duplicate paths, and checksum mismatches are rejected before commit
4. path traversal and compression-bomb fixtures are rejected
5. unknown extension data survives import/export
6. unresolved legacy links remain visible and repairable
7. forced failures at each commit stage leave the existing project readable
8. export from Windows imports on Android and the reverse
9. archive export does not contain excluded privacy fields
10. restore health is derived from a successfully validated archive

### Implementation evidence, August 17, 2026

The initial normalized connected-graph archive core is implemented in `lib/archive/authoros_archive.dart` using `archive 4.0.9` and `crypto 3.0.7`.

Passed automated checks:

- records, manuscript-node references, and typed links round trip with stable IDs
- unknown extension JSON survives archive export/import
- unchanged creative content produces the same fingerprint despite different archive IDs, dates, and platforms
- each declared data entry is validated against manifest size and SHA-256 in both manifest and checksum file
- unexpected, missing, duplicate/case-folded, absolute, drive-qualified, backslash, NUL, and parent-traversal paths are rejected
- archive entry-count and decompressed-size limits are enforced
- canonical dangling links fail domain validation
- validation completes before the repository commit callback runs
- a corrupted import leaves an already restored Drift database unchanged

Remaining before the full ADR-0005 gate passes:

- managed asset entries and checksum round trips
- structured scene/note document entries
- migration and unresolved-reference reports
- malicious compression-ratio and oversized-image fixtures
- staged asset commit/rollback
- Windows-to-Android and Android-to-Windows exchange
- restore-health integration with the application backup UI

## Consequences

### Positive

- Portability is independent of Drift table layout.
- Large projects can stream rather than load entirely into memory.
- Integrity and migration provenance are inspectable.
- Cross-platform restore can be tested with stable fixtures.
- User backups include managed assets instead of only text JSON.

### Costs

- Export/import requires explicit adapters for every domain component.
- Deterministic normalization and checksumming add implementation complexity.
- ZIP security limits and staged atomic import require substantial tests.
- Rich-text content needs a versioned document schema.
